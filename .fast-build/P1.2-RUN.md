# P1.2 Run Plan

## Done predicate

- An authenticated owner can explicitly create, list, explain, edit, and delete general shared memories.
- A new authenticated conversation can use only a small bounded set of that owner's memories as untrusted context.
- Saved recipient names and addresses continue to come only from `saved_recipients` and its existing confirmation flow.
- Chat deletion leaves shared memory intact; wallet switching cannot display stale owner data.
- A disposable database already at migration 0007 can apply additive migration 0008 while existing ledger evidence stays unchanged.
- Relevant tests, typecheck, lint, build, and diff check pass. No production DB write, wallet transaction, push, or deploy occurs.

## Scope and rigor

Estimated scope: one additive table/migration, one domain service and authenticated API surface, one assistant context seam, one memory management surface, and targeted DB/browser coverage. Rigor is high because owner-isolated personal data reaches an LLM prompt and must not cross into payment authorization. Production migration and release are out of scope.

## Architecture grounding

- `saved_recipients` already owns recipient labels and addresses. Reuse its service and explicit address confirmation; never copy recipient data into shared memory.
- SIWE claims provide owner identity. Request-body owner values are not trusted.
- Conversation sessions/messages, shared memory, saved recipients, and payment records stay separate.
- Memory context is optional, bounded, labeled untrusted, and cannot set an intent or bypass a fresh review.
- Migration 0008 is tested only on the disposable database with 0007 already applied.
