# P1.1 Persistent Chat Sessions

## Framing

- Experience goal: an authenticated wallet owner can return to a readable conversation and continue it, while payment authorization still starts from a fresh B3 review.
- Definition of done: sessions and messages persist in separate tables; every read and write derives owner from SIWE; retries do not duplicate message rows; wallet changes clear owner-bound UI and ignore stale responses; new chat, restore, continue, title, rename, delete, and paginated recent history work; desktop sidebar and mobile drawer are keyboard-accessible; no stored action, intent, approval, signature, or payment record is replayed from chat history.
- Scope estimate: one additive migration after `0006`, two tables, a small session repository and API surface, integration with the existing chat route and assistant hook, session navigation UI, migration and owner-isolation tests, and the required build/browser checks.
- Rigor: high because conversations are private wallet-owned data and schema changes can affect account isolation. All database verification must target a disposable local Postgres instance. Production migration, deployment, and release remain outside this work.
- Grounded constraints: the current chat route is stateless; no session/message tables exist; SIWE owner claims are the only ownership authority; saved recipients and payment ledgers remain separate; chat does not execute B3/B5 operations.
- Default: persist only when `requireOwner` verifies a SIWE session. Keep existing unauthenticated assistant use ephemeral. P1.1 stores readable text only, never an actionable payment payload. A structured receipt pointer remains unmodeled.

## Throughput checkpoint

- Blocking first steps: trace the current chat request/response, SIWE owner boundary, migration conventions, saved-recipient isolation, and B3/B5 call sites. Inspect migration 0006 and check for a safe local Postgres path.
- Independent workstreams: architecture candidates and migration/owner model; code implementation and session UI; local migration fixture and browser/API verification. Keep the schema and shared chat API owned by one implementation worker.
- Shared mutable state: wallet owner, active session, messages, and payment drafts must not be duplicated across hooks. The session controller is the source for the active session and transcript. Existing payment state remains owned by the assistant/payment flow and is cleared on session and wallet changes.
- Smallest safe decomposition: one worker owns the migration, repository/API, chat integration, UI, tests, and state updates in an isolated worktree. Root owns architecture, migration review, independent diff review, and final verification.
