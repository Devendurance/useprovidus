# P1.1 Conversation Session Architecture

## Decision

Use two additive tables, `conversation_sessions` and `conversation_messages`. Keep the current `useAssistant` hook as the single owner of the selected session, visible transcript, and transient payment context. The server stores plain text and safe turn state. It does not store payment actions, B3 intents, approvals, signatures, or payment records.

Candidate A is the base. Candidate B's explicit retry status is grafted onto the user message row. The cross-judge preferred A's composite owner foreign key and smaller table count, while the explicit status avoids inferring failures from missing assistant rows. The selected shape keeps both strengths without a third turns table.

## Data shape

`conversation_sessions` stores a server-generated UUID, immutable SIWE owner, title and title source, timestamps, and a client-generated create request key. `(owner_address, create_request_id)` is unique, so retrying New chat returns the same server session. `(id, owner_address)` is also unique for the message foreign key.

`conversation_messages` stores a server-generated UUID, session ID, owner address, sequence, client turn UUID, role, plain text, and database timestamp. User rows also store `pending`, `complete`, `failed`, or `superseded` turn status, a server attempt ID, lease expiry, attempt count, and a safe failure code. Assistant rows have no turn status or lease fields. A composite foreign key from `(session_id, owner_address)` to the session prevents cross-owner attachment. Unique indexes prevent duplicate user or assistant rows for a turn and permit only one pending turn per session.

The service locks the owned session while it claims a turn and allocates sequence numbers. A retry uses the same turn UUID. A pending turn with a live lease returns an in-progress conflict. A retry can claim an expired lease with a new attempt ID. Completion checks that attempt ID before inserting assistant text, so a late response from an older request cannot overwrite a newer attempt. A failed turn can be retried while it remains the newest user turn. Sending a new turn supersedes an older failed or expired turn.

## Ownership and API boundaries

Every conversation route calls the existing SIWE owner helper. The owner comes from the verified session cookie. A client wallet address is never an ownership input. Foreign and missing session IDs both return 404.

`POST /api/assistant/chat` keeps its existing ephemeral mode. Persistent mode requires a verified SIWE owner, a server session ID, and a stable turn UUID. It ignores browser-supplied history and loads recent text from the owned session. It persists the user's text before B6 runs, then persists only the assistant text. A completed retry returns saved text with no action or intent payload. A new payment request still needs a fresh B3 review.

Loading a session restores text only. The UI clears payment drafts when it changes sessions or owners. It never reconstructs prior payment cards, approvals, expired intents, or wallet actions from messages. Receipt links point to the existing receipt surface and do not duplicate payment evidence.

## Interaction shape

The desktop assistant gets a collapsible recent-conversation sidebar. It contains New chat, the active row, rename, delete, and paginated history. The transcript remains the main reading surface.

On mobile, the same list opens in a focus-managed drawer with Escape, outside-click, and selection dismissal. Opening the drawer locks background scrolling. All controls have 44-pixel minimum touch targets. Session changes close the drawer and clear transient payment state.

Delete uses an explicit confirmation that says the conversation and its messages will be removed. Payment, receipt, and saved-recipient records remain separate.

## Migration and release gate

Migration `0007` adds only the two conversation tables and their indexes and constraints. Before applying it, a local harness seeds synthetic records for two owners into the existing Celo transaction, saved-recipient, transfer-intent, and transfer-submission tables. It captures per-table row counts and SHA-256 checksums. After `0007`, the harness compares those values and checks the migration journal. The database is the disposable Postgres 16 instance at `127.0.0.1:55432`.

No production snapshot or restore procedure has been verified. Before a future production migration, the release owner must review a full backup, validate a restore in an isolated database, record table counts and owner-isolation checks, and define application rollback. The additive tables should remain during an app rollback. Do not apply this migration to production without separate authorization.
