# P1.1 Grounding

## Current product path

- `components/assistant/assistant-panel.tsx` renders the assistant surface. `hooks/use-assistant.ts` owns the in-memory transcript and payment UI context.
- `send()` appends a user message locally and posts text, bounded client history, and transient context to `/api/assistant/chat`.
- `app/api/assistant/chat/route.ts` validates and bounds that history, removes historical intent payloads, verifies SIWE owner context, and calls `resolveAssistantTurn`.
- The chat route is stateless. It does not create payment intents or submit transactions. B3 preparation remains in `/api/transfers`, and B5 submission/status remain in their own owner-scoped routes.
- Wallet/account changes already advance a context revision, abort in-flight chat requests, clear the transcript and payment draft, and ignore stale responses.

## Identity and existing records

- The HttpOnly `providus_session` cookie holds an HMAC-signed SIWE session. `authenticateRequest` verifies it. `requireOwner` derives the owner from those claims. The optional wallet header only detects a mismatch.
- `saved_recipients`, `agent_transactions`, `wallet_transfer_intents`, and `transfer_submissions` are separate owner-scoped domains. Session messages must not become the source of truth for recipient, payment, receipt, or approval records.
- No conversation or message tables exist. The Drizzle journal ends at `0006_brief_green_goblin`, so the next migration is additive `0007`.

## Product constraints

- Persist only for a currently authenticated SIWE owner. Preserve unauthenticated chat as ephemeral.
- Persist text and a minimal idempotency key. Never persist or restore wallet signatures, approvals, active payment actions, expired intents, or payment instructions.
- A returning payment request must produce a fresh B3 review. B5 remains authoritative for payment verification. Existing verified cards and the Receipts route remain the proof surfaces.
- Session deletion must confirm that only session/message history is removed. Payment, recipient, and receipt records stay intact.

## Migration verification

- Root process `DATABASE_URL` was absent. Docker Desktop was started locally and its daemon reports version 29.6.1.
- Use a disposable local Postgres container and explicit local-only `DATABASE_URL` for migration tests. Never fall back to a configured or production database.
- Seed existing ledger tables in the disposable database before applying `0007`, then assert their rows and owner values remain unchanged afterward.
- No production snapshot or restore procedure was verified. The production migration remains gated on a reviewed backup/restore plan and explicit release authorization.
